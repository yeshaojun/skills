# Loctek Test Req

把需求文档转化为可回溯的测试基准线：识别业务分类与关联、以测试视角总结业务逻辑、提取改动功能点并绑定 REQ 编号。产出是下游两个 skill 的共用输入——`loctek-test-case` 拿它做用例章节划分与追溯分母，`loctek-test-review` 拿它做需求-代码一致性基准。

## 与 loctek-issue 的分工

- `loctek-issue`：开发视角，把需求拆成可领取的垂直切片 issue。
- 本 skill：测试视角，把需求提炼成测试语言（实体/状态机/规则/依赖/异常）。
- 两者互为输入：issue 的验收标准可作为本 skill 的输入；本 skill 的 REQ 基线可反向补强 issue 的验收标准。

## 工作流

### 1. 收集输入

| 输入 | 处理 |
| :--- | :--- |
| 本地文档（.md/.docx/.pdf） | 直接读取 |
| Wiki/网页链接 | 完整抓取（含嵌套链接），失败时明确报告 |
| `.changes/issues/` 关联 issue | 验收标准/测试计划字段直接并入功能面，不重复拆解 |
| `.changes/qa/knowledge/` 或 `docs/qa/` 知识库 | 存在则检索，历史问题写入报告的回归关注点 |

文档与链接必须提供一个，否则询问用户。

### 2. 目录驱动检查

先输出文档层级目录，逐项标记提取状态，防止遗漏。区分"业务诉求"与"功能方案"：只写入明确存在交互、规则或后台落地的功能模块；只输出源文档实际提及的内容。

### 3. 四趟分层提取

按顺序逐趟输出，每趟完成后继续下一趟（禁止一次性输出）：

1. **Pass 1 功能面**：功能点清单、业务实体与状态机、本期交付/排除项/重点项。
2. **Pass 2 规则面**：字段约束表、隐性规则（标注【推导】）。
3. **Pass 3 依赖面**：上下游接口契约、存量与兼容性规则。
4. **Pass 4 异常面**：业务/系统异常、边缘场景、NFR、测试数据生成规则。

详细提取目标与输出格式见 `references/01-需求分析报告模板.md`。

### 4. 生成报告

写入：

```text
.changes/qa/req-analysis/需求分析-{需求或issue名}.md
```

frontmatter 含 `type: qa-req-analysis`、`branch`、`issue`（无关联写 null）、`status`。报告结构严格按模板：摘要与追踪 → 核心业务逻辑 → 系统交互与依赖 → 异常与边界 → 测试数据准备 → **风险与缺口（强制）**。

### 5. 用户确认基线

报告输出后，明确提示：REQ 编号是后续用例覆盖率的分母、走查一致性检查的基准，请确认或修订后再进入用例设计。

## 约束（强制）

1. **源约束**：不知道就闭嘴。未在文档中明确提及或无法逻辑推导的内容只能进"风险与缺口"，不得写入正文。
2. **编号绑定**：每个测试点绑定 REQ-* 编号，来源位置必须可在原文精确定位，禁止编造 ID。
3. **无幻觉**：禁止"通常""一般来说"等通用表述。
4. **目录驱动**：必须先输出目录映射再逐项提取。

## 完成标准

- 报告在 `.changes/qa/req-analysis/`，frontmatter 完整。
- 四趟提取全部完成，目录映射无遗漏标记。
- 风险与缺口章节非空（至少写明"未发现"及检查范围）。
- 用户已确认 REQ 基线。
