## 一、需求特征→维度组合矩阵

面对一个特定需求时，AI 应根据其所包含的**业务与技术特征**，以"套餐"的形式直接匹配对应的【核心设计方法】与【重点测试类型】。

| 需求特征与业务切面 | 必选核心设计方法 | 必选重点测试类型 | 深度执行要求与避坑指南 |
| :--- | :--- | :--- | :--- |
| **【表单与查询】** 复杂表单录入、多条件灵活组合查询 | 等价类划分 + 边界值 + 判定表 + (若联动)因果图 | 易用性（判空/报错）+ 安全（防注入） | **避坑**：不能只测组合！必须穷举字段长度极限、非法字符（表情包/全角）、数据类型越界；强联动筛选项必须验证互斥逻辑。 |
| **【状态与流转】** 明确单据生命周期、审批流、有限状态机流转 | 状态迁移法 + 场景法 | 安全（防跨节点越权） | **避坑**：验证【合法路径】只是及格，必须穷举【所有非法/跨越状态操作】并断言系统给出阻断提示（如已取消订单不能支付）。 |
| **【微服务与外部对接】** 强依赖外部供应商API、MQ上下游消息、回调 | 场景法（主链路） + 契约测试 | 可靠性（超时/降级/熔断/死信） | **避坑**：永远把外部系统当做"会崩溃的黑盒"。必测下游接口**响应超时（如10s不通）**、**返回 500** 或**脏数据**时，本应用能优雅降级而不雪崩。 |
| **【资金与交易核心】** 涉及计费、打款、发券、核心规则权重调整 | 边界值极限分析 + 错误推测法 | 安全越权 + 跨端数据一致性 | **避坑**：防护极值（如零元、巨额溢出导致负数）；核心断言必须是严格的**三线对齐**：`UI展示金额 == 数据库落表精度 == 下游划扣结果`，严防精度丢失。 |
| **【高频并发与热点】** 抢单、秒杀、大促爆点、网速慢时的疯狂连击保存 | 错误推测法 + 正交表法 | 性能专项（防重/防抖/并发竞态） | **避坑**：前端挡板不可信！除了页面防抖，强制构造"两笔相同的API写请求同时到达后端"，断言**接口层实现了严格锁机制或幂等**，不双重落库。 |
| **【历史兼容与基建重构】** 老表加字段、逻辑重构、数据清洗迁移 | 判定表 + 分类树法 | 兼容性测试（历史脏数据）+ 回归 | **避坑**：致命的往往是老数据崩盘。用新兵测新规的同时，必须找出**缺失新环境字段的几年存量老数据**，验证它们走老逻辑不抛 500、可正常回显。 |
| **【权限与多租户体系】** B端SaaS体系、矩阵式角色/数据隔离管控 | 判定表（覆盖角色授权网） | 安全测试（纵向越权/横向越权） | **避坑**：正向鉴权易，反向越权难防。必须验证：1. 低权角色直调高权接口；2. A租户伪造ID访问B租户的私密库表（必须抛404/403，数据硬物理/逻辑隔离）。 |
| **【终端适配与重交互】** 大屏数据面板、复杂工作台、长列表、图表回显 | 错误推测法（极值排版） | 易用性 + UI跨设备跨核兼容 | **避坑**：重点构造"丑陋数据"：查询结果0条的空态插画、名字超过100个字的省略号截断（不撑爆CSS盒子）、1080P小屏下的横向滚动与折行处理。 |
| **【批处理与异步计算】** 定时任务拉取、月底出财务报表、大Excel导出 | 边界值分析 + 错误推测法 | 性能（内存/慢SQL）+ 可靠性 | **避坑**：百万级数据量下的处理极易 OOM。必须覆盖触发导出后去执行其他操作的进度感知、导出失败的重试链路，及定时任务挂掉或被并发触发的锁处理。 |
| **【即时通讯与长连接】** 站内信红点推送、WebSocket聊天、App PUSH | 状态迁移法 + 场景法 | 易用性（即时反馈）+ 兼容性 | **避坑**：切忌只测两人都在线。必须测**离线后重连的消息追齐**、**多端登录（PC/App）时的消息同步阅读状态**、断网环境下的超时未达反馈。 |
| **【规则引擎与算法策略】** 风控扣分、派单匹配算法、动态路由策略 | 判定表（规则穷举） + 因果图 | 准确性验证 + 边界临界点验证 | **避坑**：多因子计分模块，绝对不能只测"显然命中"。必须测**刚好差1分未命中**、**刚好压线达到阈值**，以及多个互斥条件同时满足时的系统兜底默认生效策略。 |
| **【文件资源与云存储】** OSS附件上传与下载、切片传输、资源库预览 | 等价类 + 边界值法 | 安全（防毒/鉴权） + 易用性 | **避坑**：后缀名欺骗上传（如.exe改.jpg）、单文件极值（如超大视频导致OOM或超时挂断）、无权限者通过直接猜OSS直链越权下载私密文件。 |
| **【搜索与推荐排序】** ES查询列表、模糊分词打分、千人千面冷启动推荐 | 场景法 + 错误推测法 | 易用性（高亮/空态）+ 性能验证 | **避坑**：必须测非标准中文分词（同音字、拼音搜索断连）；验证分页极限（翻到1000页时深翻页导致的慢查询崩溃）；验证打分相同时的默认次级排序原则（如按时间）。 |
| **【营销权益与会员体系】** 积分生命周期、优惠券互斥合并、等级自动升降 | 状态迁移法 + 判定表 | 安全（防薅羊毛） + 一致性 | **避坑**：必须追溯资产全生命周期。重点覆盖：优惠券超发超兑并发、满减与其他折扣互斥逻辑（多优惠叠加防击穿成负数）、资产过期日临界点的自动注销准点性。 |
| **【多端协同与单点登录】** 同账号多设备接力、一端操作另一端被挤占 | 场景法 + 状态迁移法 | 兼容性 + 安全（Token过期回收） | **避坑**：防状态不同步。重点覆盖：A端修改密码后B端立刻发起调用是否被拦；A/B两端同时编辑同一表单，谁的变更被覆写（乐观锁控制）；App与小程序的兼容流转。 |
| **【埋点监控与日志追溯】** 业务转化漏斗上报、停留时长抓取、核心动作打点 | 场景法（主执行路径） | 可靠性（日志防丢）+ 性能消耗 | **避坑**：容易变成盲区。必须在弱网/断网环境下切断上报，观察恢复网络后是否做堆积补偿上报（防漏）；必须确保打点报文错误时，决不卡死阻塞用户的正常主业务流程。 |
| **【时区与国际化I18n】** 跨境电商发品、外包工单、跨国时区计时结算 | 等价类（语言包）+ 边界值 | 易用性（文案超长）+ 安全越权 | **避坑**：不同语种字符长度差异导致按钮错位；最危险的是**客户端当地时间与服务器时区偏移**，必须测通过修改客户端系统时间企图"提前解锁明天才发售的商品"被系统拦截。 |
| **【身份认证与防刷风控】** OTP短信、人脸库比对、验证码拦截与风控滑块 | 因果图 + 错误推测法 | 安全（暴库/刷量）+ 易用性 | **避坑**：不仅验证能收到短信；重点攻击验证码机制：能否无脑狂点刷爆短信费（频率限制）、验证码能否多次重复使用（用后即焚）、滑块能否被脚本直接篡改坐标绕过。 |
| **【配置驱动型业务控制】** 后台配置面板（开关/阈值/枚举），配置落库后驱动下游硬件控制（断电/断水/门锁）或支付拦截等实际业务行为 | 判定表（穷举配置项组合 × 业务场景结果） + 场景法（E2E 验收链路） | 功能测试（CRUD） + 业务场景验证（下游联动） + 兼容性（历史无配置数据兜底） | **避坑（极致重要）**：❌ 绝不能只测「后台表单能保存」就收工！配置类需求的本质是**配置是手段，下游业务行为才是测试终点**。必须用判定表穷举所有「开关值 × 阈值临界 × 联合条件」的组合，并逐一验证下游系统的实际执行结果（如：欠费>阈值 + 配置断电=是 → 验证设备是否真正断电；充值恢复后 → 验证通电通水）。特别注意：**多维度配置的「或/且」联合判定**以及 **E2E 验收流程**（从签约→欠费→冻结→充值→解冻的完整业务闭环）。 |
| **【流媒体与图形渲染】** 大图缩放剪裁、长视频/直播拖拽倍速 | 错误推测法（异常流） | UI视觉测试 + 性能（显存/卡顿） | **避坑**：切忌只点播放。必须测视频缓冲中途拖拽进度条、网络断开再连画音同步、不支持的编码格式兜底（提示降级或纯黑屏）、直播流断推时的黑场平滑过渡展示。 |

## 二、复杂多条件与多节点审批链路穷举规则

> **核心痛点**：AI 生成用例时，一旦面临**多个独立的前置配置/多级审批节点**，往往只生成有限的「主干正向」加「单一负向」，严重遗漏多维度的笛卡尔积漏测隐患。

### 强制执行规则

遇到包含**「多个独立判定条件」、「多级并行或串行审批节点」或「多端状态机联动判断」**的业务链路时，AI **不得仅挑选2~3条代表性路径**，必须强制使用**【判定表法/正交法】**将所有业务上「可能同时发生」的条件组合完全展开，保证所有可能影响最终落库状态的组合情况，全量生成独立用例。

### 深度打透步骤模式

**Step 1 - 因子提取与水平排列**

抽取所有影响结果的变量节点并列举其所有合法返回值。
例如：
- 节点A：安审（通过/失败/未触发）
- 节点B：SSC人工审（通过/失败/待审）
- 节点C：政府核验（通过/驳回）

**Step 2 - 构建矩阵全量展开**

在草稿（思考过程）中铺开所有逻辑组合矩阵。上述三个节点将展开为 3×3×2=18 种组合。

**Step 3 - 剪枝去噪（短路逻辑）**

若某一步「彻底失败」会导致后续流程阻断并拦截短路，则将这些短路分支合并剪枝；凡是能走到底的「非阻断」分支，全部保留。

**Step 4 - 1对1独立落盘用例**

对剪枝后留下的所有有效「横向组合矩阵行」，每一行**必须单独对应输出至少一条用例**，并在【预期结果】中精细对齐各组合引起的下游差异动作。

> ❌ **绝对禁止**：在一条用例里用「分别测试XXX组合及其结果」一笔带过。

### 典型灾难现场示例

假设：安审、SSC审核、政府核验三个节点，安审包含 3 个结果，SSC包含 3 个结果，政府核验包含 2 个结果。

**AI 错误做法**（严重遗漏）：
- TC-001：三个都通过，划为A类。
- TC-002：安审命中C类报错。
- TC-003：SSC人工命中B类仅展示。
- *【遗漏】若`安审命中B` 且 `SSC也命中B` 且 `政府不支持`...怎么流转？没有写出相应的验证用例*。

**正确做法**：
1. 遇到此类多维度多节点特征的需求，绝对禁止靠脑内联想来挑选分支。
2. 必须列出完整判定表并剪掉因「前置阻断」产生的无效冗余行。
3. 剩余的所有组合矩阵行，每一行都必须实实在在地成为标题独立、前置明确、断言精准的**单个具体测试用例**。
