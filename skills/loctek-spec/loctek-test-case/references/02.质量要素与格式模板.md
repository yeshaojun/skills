# 用例质量要素详细定义与格式模板

## 一、8 大质量要素详细定义

> ⚠️ 以下每个要素缺失时，系统仍需正常生成并输出该条用例，但**绝对禁止**进行模糊编造，必须在该要素位置打上醒目的待充填标记（`【⚠️ 待确认】`），交由人工后续补充。

---

### 要素 1：唯一编号

- **格式**：`TC-{模块缩写}-{三位序号}`，如 `TC-AUTH-001`
- ✅ 合格：`TC-ORDER-003`
- ❌ 不合格：无编号、`TC-1`、与其他用例重号
- ⚠️ 容错输出：若无法判定归属模块，输出 `TC-【⚠️待分配模块】-001`

---

### 要素 2：需求追溯

- **格式**：精确到 需求文档或Wiki 章节编号 + 章节名称 / 流程图节点名称
- ✅ 合格：`Wiki §3.2「触发建单条件」/ 流程图节点「用户回复后自动建单」`
- ❌ 不合格：`PRD 相关章节`、`需求文档`
- ⚠️ 容错输出：若章节编号不明确，输出 `Wiki【⚠️待确认章节】/ 流程图节点「XXX」`

---

### 要素 3：明确前置条件

- **要求**：精确描述数据状态（非「正常数据」）、账号权限、系统环境配置
- ✅ 合格：`存在 owner_id=12345 的用户，该用户有 1 笔绑定订单（order_id=67890），当前无待处理订单`
- ❌ 不合格：`有用户的数据`、`正常账号`、`测试环境`
- ⚠️ 容错输出：若缺失条件详情，输出 `前置条件：基于【⚠️ 需补充精确用户状态】，当前无待处理订单`

---

### 要素 4：数据造数步骤

- **要求**：显式说明如何构造依赖数据，提供 DB SQL 或页面操作路径
- ✅ 合格：`执行 SQL：INSERT INTO owner_order (owner_id, status) VALUES (12345, 'active'); 或访问 {测试环境URL}/admin/owner 创建用户绑定订单`
- ❌ 不合格：`准备测试数据`、`造一个有订单的用户`（无具体操作路径）
- ⚠️ 容错输出：若知识库未找到匹配造数方法，输出 `依赖数据构造：【⚠️ 暂无可用造数脚本，需补充】`

---

### 要素 5：操作步骤

- **要求**：步骤编号，每步只有一个动作，步骤间有清晰的前后依赖
- ✅ 合格：`1. 打开 {env_url}/im/group-list  2. 找到用户群聊 ID=XXX  3. 点击「发起聊天」按钮`
- ❌ 不合格：`打开页面，找到对应用户，点击发起聊天，等待回复，检查工单`（多步合一）
- ⚠️ 容错输出：若遇到无法拆解的隐藏动作，输出 `3. 【⚠️ 需明确具体点击的入口标识】执行发起聊天`

---

### 要素 6：双线预期结果

- **要求**：预期结果必须同时包含 UI/响应层 + DB/下游层，缺一不可（纯展示类功能无 DB 操作的情况下，标注说明原因即可）
- ✅ 合格：`💻 UI：页面出现「聊天已发起」Toast；📡 DB：SELECT * FROM work_order WHERE owner_id=12345 查到新增记录，status='pending'`
- ❌ 不合格：`工单建立成功`（无层次细化）、`只有 UI 描述无 DB 核验`
- ⚠️ 容错输出：若无法判定具体数据库表结构，输出 `💻 UI：页面出现提示；📡 DB：【⚠️ 需确认落库表与目标字段结果】`

---

### 要素 7：用例标签

- **要求**：标注所属测试维度与具体的**测试类型**标签，不能只标常规阶段，必须落实到**具体的测试领域**。
- ✅ 常规维度合规标签：`🏷️ 黑盒-功能`、`🏷️ 黑盒-正向`、`🏷️ 黑盒-边界`、`🏷️ 黑盒-异常`、`🏷️ 黑盒-回归`
- ✅ 专项合规标签：`🏷️ 黑盒-安全防护`（XSS/越权）、`🏷️ 黑盒-性能防重`（高并发）、`🏷️ 黑盒-老数据兼容`、`🏷️ 黑盒-网络可靠性`（降级/超时）、`🏷️ 黑盒-弱网兜底`
- ❌ 不合格：无标签、或脱离测试类型的假大空词
- ⚠️ 容错输出：若实在无法精确归类，输出 `🏷️ 黑盒-【⚠️待定测试专项分类】`

---

### 要素 8：优先级定级

- **要求**：根据业务重要度和执行频率，明确划分为 P0/P1/P2

| 优先级 | 含义 | 示例场景 |
| :--- | :--- | :--- |
| **P0** | 冒烟功能/阻断级 | 核心业务主流程、支付链路、登录鉴权 |
| **P1** | 主干流转/核心异常 | 主要分支流程、重要异常拦截、权限验证 |
| **P2** | 边界容错/全面覆盖 | 边界值分析、小概率异常场景、兼容性验证 |

- ❌ 不合格：无优先级配置、使用 `高/中/低` 等非标准描述
- ⚠️ 容错输出：若无法研判风险，输出 `优先级：【⚠️待定级】`

---

## 二、完整用例格式模板

```markdown
### TC-{模块}-{编号}: {用例名称} 🏷️ [黑盒-正向 / 黑盒-边界 / 黑盒-异常 / 黑盒-回归]

**优先级**: [P0 / P1 / P2]

**测试目标**: 一句话描述本用例核心验证点。（使用 PRD 原话，禁止过度修饰）

**需求追溯**: Wiki 章节名称 / 流程图节点名称（精确到具体条目）

**前置条件**:
- 精确的数据状态描述（如：存在状态为「处理中」的工单，工单ID=XXX）
- 账号权限要求（如：账号已配置 owner_service_create_session 权限；权限配置操作参见通用能力知识库/安家权限操作.md）
- 系统配置要求（如：规则引擎已配置XXX执行动作且为最高优先级）
- 测试环境：{从数据构造知识库/系统基础信息.md 获取的真实环境 URL}

**依赖数据构造**:
- 造数方式：[页面操作路径 / DB SQL 脚本]
- 具体 SQL（优先从数据构造知识库获取，无则标注「⚠️ 待补充」）：
  ```sql
  INSERT INTO table_name (col1, col2) VALUES ('val1', 'val2');
  ```

**适用页面/接口**: {精确页面名称 或 API Endpoint（含真实域名）}

**测试步骤**:
1. [操作单一，动作明确，每步只有一个原子操作]
2. [进入具体入口页面]
3. [执行目标操作]
4. [观察/验证结果]

**预期结果**:
- 💻 **UI / 响应反馈**: [页面展示、弹窗提示、按钮状态、响应码等]
- 📡 **下游处理**: [DB 字段值（附 SQL 查询语句）、消息发送、下游状态变更等]
```

## 三、测试概览表格式（文件头部必须包含）

*说明：本概览表每行严格对应**一个且仅一个原子测试点**，双向追溯至原始 PRD 章节。*

**强制要求**：
1. 每条测试用例与本概览中的测试点 **1:1 严格对应**，不能漏测，不能多个测试点合并成一行。
2. **用例原子化红线**：若测试点描述中出现「及/同时校验/和」连接两个独立校验目标，必须先拆分再填写。
3. 每行必须明确标注**测试方法**与**测试类型**。

| 用例编号 | 对应需求描述 (Wiki 章节/动作) | 测试点概述（单一原子） | 测试方法 | 测试类型 |
| :--- | :--- | :--- | :--- | :--- |
| TC-001 | [需求 3.1 章节 / 流程图右侧分支] | [一个极致提取的原子校验点] | [等价类划分 / 边界值 / 场景法 / ...] | [功能测试 / 安全测试 / 易用性 / ...] |
