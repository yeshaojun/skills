## 一、需求条目提取规则

> **核心原则**：需求条目是追溯的原子单位，粒度太粗则无法精确校验、粒度太细则不可管理。以下规则确保提取粒度恰当。

### 1.1 提取粒度标准

每个 REQ 条目必须满足"**可独立验证**"原则——即可以设计出至少一个明确的测试步骤 + 预期结果来验证该条目。

| 粒度 | 是否合适 | 示例 |
| :--- | :--- | :--- |
| ✅ 恰当粒度 | 单一可验证规则 | `REQ-003: 当用户欠费 > 配置阈值时，系统自动外呼` |
| ❌ 太粗 | 多个规则聚合 | `REQ-003: 用户欠费管理功能` |
| ❌ 太细 | UI 像素级细节 | `REQ-003: 自动外呼提示文案的字体为14px` |

### 1.2 必须提取的来源

按优先级排序，以下来源中的可测试内容**必须**被提取为 REQ 条目：

| 来源类型 | 提取方式 | REQ 条目 ID 前缀建议 |
| :--- | :--- | :--- |
| **流程图判断节点** | 每个 Yes/No 分支独立成条目 | `REQ-FLOW-` |
| **业务规则描述** | 每条规则独立成条目 | `REQ-RULE-` |
| **表单字段定义** | 每个含校验规则的字段独立成条目 | `REQ-FIELD-` |
| **操作按钮/交互** | 每个按钮的正向行为成条目 | `REQ-UI-` |
| **权限约束** | 每条权限规则独立成条目 | `REQ-AUTH-` |
| **配置项→业务联动** | 每个配置项的下游业务效果成条目 | `REQ-CFG-` |
| **接口协议字段** | 每个关键入参/出参的校验规则成条目 | `REQ-API-` |
| **非功能性约束** | 每条性能/降级/兼容要求成条目 | `REQ-NFR-` |
| **技术文档中的枚举/状态** | 每种状态的合法/非法转换成条目 | `REQ-STATE-` |

### 1.3 歧义处理规则

| 场景 | 处理方式 |
| :--- | :--- |
| PRD 描述模糊，无法确定是否含可测试逻辑 | 创建条目并标注 `⚠️ 需PRD确认` |
| PRD 涉及多个子条件的组合判定 | 将组合判定作为一个规则条目，后续在用例生成时用判定表展开 |
| PRD 的文字描述与截图/设计稿不一致 | 创建两个条目分别记录，标注冲突点 |
| 技术文档补充了 PRD 未提及的约束 | 以技术文档为准创建条目，标注来源为技术文档 |

## 二、双向追溯矩阵构建方法

### 2.1 正向追溯矩阵（需求→用例）

**目的**：确保每个 REQ 条目至少被一条用例覆盖。

**构建方法**：
1. 以 REQ 基线表为行索引
2. 扫描所有已生成用例的「需求追溯」字段
3. 将对应的 TC-XXX 编号填入矩阵

```
正向追溯矩阵：
| REQ-ID | 覆盖的用例列表 | 覆盖数量 | 覆盖状态 |
| :--- | :--- | :--- | :--- |
| REQ-001 | TC-WO-001, TC-WO-002 | 2 | ✅ |
| REQ-002 | TC-WO-003, TC-WO-004, TC-WO-005 | 3 | ✅ |
| REQ-003 | （无） | 0 | ❌ 待补充 |
```

### 2.2 逆向追溯矩阵（用例→需求）

**目的**：确保每条用例都能追溯到有效的需求来源，防止"幻觉用例"。

**构建方法**：
1. 以用例编号为行索引
2. 检查每条用例的「需求追溯」字段是否包含有效的 REQ-ID
3. REQ-ID 不在基线表中的视为"孤儿用例"

```
逆向追溯矩阵：
| TC-ID | 追溯到的 REQ-ID | 追溯状态 |
| :--- | :--- | :--- |
| TC-WO-001 | REQ-001 | ✅ 有效 |
| TC-WO-010 | REQ-007 | ✅ 有效 |
| TC-WO-025 | （无有效REQ） | ⚠️ 孤儿用例 |
```

**孤儿用例处理**：
- 如果是基于错误推测法产生的通用防御用例（如 XSS/SQL 注入），允许标注为 `REQ-GEN-SECURITY`（通用安全条目）
- 如果是基于回归需要产生的历史功能用例，允许标注为 `REQ-REGRESSION-{历史功能名}`
- 其他无法追溯的用例应删除或补充需求来源

## 三、覆盖度计算与达标判定

### 3.1 核心指标定义

| 指标名称 | 计算公式 | 达标阈值 |
| :--- | :--- | :--- |
| **需求正向覆盖率** | 已覆盖 REQ 数 / REQ 总数 × 100% | **≥ 95%** |
| **逆向追溯完整率** | 有有效追溯的 TC 数 / TC 总数 × 100% | **≥ 90%** |
| **异常用例占比** | 异常/边界/负向用例数 / 用例总数 × 100% | **≥ 30%** |
| **测试类型覆盖达标率** | 达标类型数 / 承诺"必须"的类型数 × 100% | **100%** |

### 3.2 未达标处理规则

| 状况 | 处理方式 |
| :--- | :--- |
| 正向覆盖率 < 95% 且未覆盖条目 ≤ 3 | 补充用例或标注合理理由后可提交 |
| 正向覆盖率 < 95% 且未覆盖条目 > 3 | **禁止提交**，必须继续补充 |
| 异常用例占比 < 30% | **禁止提交**，必须按异常输入维度补充 |
| 测试类型覆盖达标率 < 100% | **禁止提交**，必须为未达标类型补充用例 |
| 孤儿用例占比 > 10% | 需检查是否存在需求条目提取遗漏 |

### 3.3 跳过覆盖的合法理由

以下理由允许将某个 REQ 条目标记为"跳过"而不计入覆盖率分母：

| 合法理由 | 标注格式 |
| :--- | :--- |
| 需求描述模糊，已提请产品澄清 | `⚠️ 跳过：需求待澄清（PRD §X.X）` |
| 该条目属于非测试范畴（纯UI样式微调） | `ℹ️ 跳过：纯视觉样式，不影响功能` |
| 该条目完全依赖于第三方实现，无法自主验证 | `⚠️ 跳过：依赖外部系统 XXX，超出测试范围` |

## 四、测试类型覆盖承诺生成规则

### 4.1 基于条目类型的自动判定

REQ 条目的「条目类型」直接触发对应测试类型的覆盖承诺：

| REQ 条目类型 | 自动触发的测试类型 | 承诺最低用例数计算 |
| :--- | :--- | :--- |
| 功能规则 | 功能测试 | 该类条目数 × 2（正向+异常各1） |
| 数据校验 | 功能测试 + 边界测试 | 每个字段至少 3 条（有效+上边界+下边界） |
| 状态流转 | 功能测试 + 状态迁移测试 | 合法路径数 + 关键非法路径数 |
| UI 交互 | 功能测试 + 易用性测试 | 每个交互元素至少 1 条 |
| 安全约束 | 安全测试 | 每条约束至少 2 条（合法+非法） |
| 性能约束 | 性能测试 | 每条约束至少 1 条 |
| 兼容约束 | 兼容性测试 | 每条约束至少 1 条 |
| 配置驱动 | 功能测试 + E2E 验证 | 配置项组合数（参考判定表展开） |
| 接口协议 | 接口测试 | 每个接口至少 3 条（正向+异常+边界） |
| 非功能性 | 可靠性测试 | 每条要求至少 1 条 |

### 4.2 基于需求特征矩阵的补充判定

当 REQ 条目类型不足以覆盖所有相关测试类型时，需参照 `03.需求特征矩阵与穷举规则.md` 中的 20 类需求特征矩阵进行补充评估：

**补充判定触发条件**：
- 需求涉及微服务调用 → 补充可靠性测试
- 需求涉及用户可见列表 → 补充易用性测试（空态/超长文本）
- 需求涉及写操作 → 补充性能测试（防重/幂等）
- 需求涉及存量数据场景 → 补充兼容性测试
- 需求涉及新增权限模型 → 补充安全测试

### 4.3 覆盖承诺的下限保障

即使自动计算的承诺用例数为 0，以下测试类型仍有**绝对最低保障**：

| 测试类型 | 绝对最低保障 | 触发条件 |
| :--- | :--- | :--- |
| 功能测试 | ≥ 10 条 | 永远触发 |
| 安全测试 | ≥ 2 条 | 需求涉及登录态或用户数据 |
| 易用性测试 | ≥ 2 条 | 需求涉及新增页面或表单 |

## 六、特殊情况处理

### 6.1 上游报告不存在时的降级策略

当 `.changes/qa/req-analysis/` 下不存在对应的需求分析报告时：

1. 在对话中声明「⚠️ 未检测到上游结构化分析报告，将从原始需求文档直接提取需求条目」
2. 从原始需求文档（Wiki/PDF/本地 .md）中手动提取 REQ 条目
3. 提取完毕后必须同样输出 REQ 基线表并请用户确认
4. 后续流程无变化

### 6.2 需求过于简单时的最低保障

当 REQ 条目总数 ≤ 5 时：
- 用例数量基准自动切换为「简单功能」级别（≥ 20 条）
- 仍需覆盖功能测试、异常测试、边界测试三个基本类型
- 测试类型覆盖承诺表中"不涉及"的类型允许不生成

### 6.3 增量需求场景

当需求为增量变更（在已有功能上修改/新增）：
- REQ 条目应同时包含新增条目和受影响的历史条目
- 历史条目标注 `🏷️ 回归` 标签
- 覆盖度统计中，回归条目与新增条目分别计算覆盖率
