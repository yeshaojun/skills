# Loctek Test Case

生成"数量充足、质量达标、追溯闭环"的黑盒功能用例。解决四类高频问题：只写正向主流程、需求条目漏覆盖、专项测试类型缺失（安全/性能/兼容等）、用例不可追溯。

## 输入

优先级从高到低，取第一个存在的：

1. `.changes/qa/req-analysis/` 下的需求测试分析报告（loctek-test-req 产出）。
2. `.changes/issues/` 中关联 issue 的验收标准与测试计划（loctek-issue 产出）。
3. 原始需求文档（.md/.docx/.pdf/wiki 链接）——此时先建议用户运行 `loctek-test-req` 建立测试基线；用户拒绝时按 `references/05.需求追溯与覆盖度验证规则.md` §6.1 降级策略直接从原文提取 REQ 条目。

有项目知识库（历史问题清单/数据库分析，通常在 `docs/qa/` 或 `.changes/qa/knowledge/`）时必须先检索：历史问题对应的检查点强制生成回归用例。

## 输出

```text
.changes/qa/blackbox/黑盒测试用例_{需求或issue名}.md
```

frontmatter 必须含 `type: qa-case-set`、`branch`、`issue`（无关联写 null），供归档与后续执行使用。

## 工作流（8 步，禁止跳步）

### Step 1 消费上游输入

需求分析报告已包含模块拆分、UI 操作元素清单、数据字典与枚举、流程拓扑、章节锚点——直接作为用例章节划分依据。跳过它从原始 PRD 重推会遗漏辅助按钮等细节。

### Step 2 建立 REQ 追溯基线（强制门控）

把所有可测试需求点拆成原子条目并分配 REQ-ID，输出基线表请用户确认后才可进入 Step 3：

```text
| REQ-ID | 需求原文摘要(≤30字) | 来源位置 | 条目类型 | 预估用例数 |
| REQ-RULE-001 | 审批超时自动通过 | §3.1 状态流转 | 功能规则 | 5 |
```

- REQ-ID 必须对应真实可定位的章节/段落，禁止为凑数编造。
- 结构相似但业务独立的配置字段（同页多个带优先级/必填的字段）必须各自独立成组。
- 条目总数是覆盖率计算的分母。

### Step 3 测试设计方法与类型承诺

方法速查：输入字段→等价类+边界值；条件组合→判定表；状态流转→状态迁移法；完整链路→场景法；会话推送→场景法+错误推测。

**6 大测试类型承诺表（强制逐一评估，排除必须写理由）**：

| # | 测试类型 | 自动触发条件（满足任一即 ✅） |
| :--- | :--- | :--- |
| 1 | 功能测试 | 永远涵盖 |
| 2 | 安全测试 | 多角色权限 / URL 参数 / 输入框 / 数据隔离 / 多租户 |
| 3 | 性能测试 | 提交按钮 / 定时任务 / 多端同操作 / 列表可能超百条 |
| 4 | 可靠性测试 | 外部服务或 MQ / 定时器 / 网络请求 / 多步事务 |
| 5 | 兼容性测试 | 改存量功能 / 新增 DB 字段 / 多端 / 删除配置后恢复默认 |
| 6 | 易用性测试 | 新增页面 / 错误提示 / 列表展示 / 长文本 / hover tooltip |

安全测试强制子规则：菜单权限必测 URL 直访越权；多租户必测横向越权；每个操作权限点必测无权限直调接口。

### Step 4 用例数量基准

| 规模 | 判定 | 最低用例数 |
| :--- | :--- | :--- |
| 简单 | 判断节点 ≤3，字段 ≤5 | ≥ 20 |
| 中等 | 判断节点 4~8，字段 6~15 | ≥ 40 |
| 复杂 | 判断节点 >8，多角色/多状态 | ≥ 70 |

红线：异常用例占比 ≥ 30%。**原子化禁止合并**：边界值逐个独立、不同字段异常独立、每个操作按钮独立、每个标签颜色组合独立。

### Step 5 分批规划

每条详述约 15-25 行；超过 40 条必须分批写入。先声明章节划分与写入批次；概览表在全部详述完成后写入（防截断导致"有索引无详述"）。

### Step 6 写入用例文件

文件结构固定为：概述 → REQ 基线表 → 方法选取 → 类型承诺表 → 测试概览表 → 详述用例 → 覆盖度报告。

**概览表第 2 列必须是 关联需求(REQ-ID)**。每条详述用例 8 要素齐全：唯一编号、需求追溯（`原文摘要 → REQ-{ID}`）、精确前置条件（含账号/URL）、依赖数据构造、原子操作步骤、双线预期（💻UI + 📡DB/下游）、标签、优先级。详述质量红线见 `references/02.质量要素与格式模板.md`。

**功能用例 7 类分支全覆盖**：正向主流程、正向分支、异常/错误、数据一致性、边界值、负向拦截、跨模块联动。每个操作按钮至少 3 类（正向/权限拦截/状态异常）。

**专项类型追加**：功能用例写完后，对照承诺表为每个 ✅ 类型追加独立章节，挖掘思路见 `references/01.四大设计维度详解.md`。配置驱动型需求必须穷举下游联动（正向触发/反向不触发/OR 联合/支付拦截/恢复解冻/删除后默认/变更后老数据联动）——不能只验证"配置保存成功"。

### Step 7 机器校验（脚本，禁止跳过）

```bash
node "<skill-dir>/scripts/validate-cases.mjs" .changes/qa/blackbox/黑盒测试用例_{名称}.md --min 95
```

脚本硬校验：概览↔详述双向差集为空、TC 引用的 REQ-ID 都在基线中、REQ 正向覆盖率 ≥ 95%、承诺类型数量达标（--strict 转为硬失败）。未通过必须修复后重跑，禁止带病交付。

### Step 8 覆盖度报告（写入文件末尾）

三张表缺一不可：REQ→TC 正向追溯表（每个 REQ 标注覆盖状态与用例列表）、测试类型达标率、设计方法使用统计。反向追溯由概览表 REQ-ID 列承担。生成前过一遍 `references/04.反模式速查手册.md`。

## 状态机与流程场景速查

- **审批流/工单流**：状态迁移法画全状态机（前置状态×操作×权限→后置状态），每个合法转移一条用例，非法转移逐条验证拦截；多条件分级用判定表；审批人与发起人联动、超时策略单独成章。
- **登录/鉴权链路**：场景法串全链路（凭证→会话→跳转→登出→会话失效），字段级等价类+边界值，安全子规则强制执行（连续失败锁定、URL 直访、横向越权、防暴力破解）。

## 自检清单（摘要）

1. 上游报告/issue 已消费，知识库已检索并注入回归用例
2. REQ 基线已输出并确认，REQ-ID 来源可精确定位
3. 7 类业务分支齐全；流程图每个判定分支有独立用例
4. 承诺表 6 类逐一评估，✅ 类型数量达标
5. 概览↔详述双向一致（脚本确认），无跳号漏号
6. 异常用例 ≥ 30%，用例全部原子化
7. 双线预期结果齐全，前置条件含具体账号与 URL
8. 覆盖率 ≥ 95%（不足需逐条标注理由），三张覆盖度表完整

## 完成标准

- 用例文件在 `.changes/qa/blackbox/`，frontmatter 完整。
- `validate-cases.mjs` 通过。
- 用户可按用例直接执行（前置条件、造数、步骤、预期自包含）。
- 需要自动化执行时，交接给 `loctek-test-run`。
